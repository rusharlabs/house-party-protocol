# Agent Framework Wizard

A 6-step wizard (`check_python → check_git → check_deps → configure → validate →
generate_and_summary`) that scaffolds a new agent/project: it generates
`operator-profile.yaml` (verification ladder R0-R4) + the chosen templates
(`00-READ-FIRST`, `00-STATE`, `00-VISION`, `00-PROCESSES`). It does not install the
`operator-kit` itself — it generates the initial skeleton a new project would use with it.

## Prerequisites + external APIs

| Requirement | Minimum version | Required? |
|---|---|---|
| Python | 3.9 | yes |
| git | any | yes — the wizard confirms `git --version` in step 2 |
| PyYAML | any | yes |

External services: **none — stdlib + PyYAML.**

## Install as a plugin

```bash
/plugin marketplace add rusharlabs/house-party-protocol
/plugin install agent-framework-wizard@house-party-protocol
```
The plugin has no hooks; the `agent-framework-scaffold` skill is auto-discovered and
`wizard.py` is reachable at `${CLAUDE_PLUGIN_ROOT}/wizard.py`.

## Install by copy

In the emitted distribution this module lives in `wizards/agent-framework-wizard-1.2.0/`
(the directory carries the version — state it once, in `KIT`). The installer is
`installers/kit-forge-1.4.1/kit_doctor.py`; run it from the distribution root. It plans
first and writes only on a second, explicit `--apply`:

```bash
KIT=wizards/agent-framework-wizard-1.2.0
cp -r "$KIT" ../your-repo/agent-framework-wizard   # the copy itself (kit_doctor does not copy on claude-code)
python installers/kit-forge-1.4.1/kit_doctor.py install --kit "$KIT" --host claude-code --target ../your-repo
python installers/kit-forge-1.4.1/kit_doctor.py install --kit "$KIT" --host claude-code --target ../your-repo --apply
# Codex CLI: --host codex — the installer copies the module into .agents/hpp/agent-framework-wizard
#            and the skill into .agents/skills/hpp-agent-framework-wizard-<skill>; no cp -r needed
```
This kit has no hooks/wiring — once copied, use `wizard.py` directly (next section).

## How to use (non-interactive — no mode blocks on stdin)

The real operator of this ecosystem is often an agent acting for the human — a terminal
`input()` hangs in exactly that context. This wizard's "Confirm" is `--interview` (prints
the question schema) followed by `--answers` (applies the answers):

```bash
# 1. print the question schema (JSON, exit 0, generates nothing)
python wizard.py --interview

# 2a. quick scaffold with sensible defaults (asks nothing)
python wizard.py --demo --out <dir>

# 2b. OR scaffold from ready answers (the agent builds the JSON after reading --interview)
python wizard.py --answers answers.json --out <dir>
```

Example `answers.json`:
```json
{"project_name": "my-agent", "templates": ["00-STATE", "00-VISION"]}
```

## What the installer detects / what the wizard detects

The installer's `detect` stage classifies the target (read-only) with exactly these three
labels; the `configure` stage carries the wizard's two questions (`project_name`,
`templates`), answered for real with `--answers <file.json|yaml>`:

```
greenfield    -> no prior config in the target; nothing to copy (the scaffold is generated by wizard.py, not by the installer)
in-progress   -> .claude/ exists, or settings(.local).json already has hooks/statusLine, or the repo has
                 more than 3 commits: reported, never overwritten
re-run        -> this kit+target pair is already in the registry (~/.claude-kits/registry.json)
```

And the wizard itself, when it generates into `<out>/docs/plans/execution/`:

```
new file      -> generates operator-profile.yaml + the chosen templates from scratch
customized    -> the file exists with content DIFFERENT from what would be generated -> skip
                 (reported in "files_skipped_customized", never overwritten)
identical     -> content identical to what already exists -> no_op:true (nothing changes, nothing breaks)
```

## What is safe to run again

`generate_and_summary()` **never overwrites** a file that already exists with content
different from what would be generated (user customisation) — the
`files_skipped_customized` field in the returned JSON lists exactly what was preserved.
Running twice without editing anything gives `no_op: true`. To force regeneration on
purpose (discarding customisation), use `--force`.

The first template and the output directory were renamed to English:
`00-LEIA-PRIMEIRO` became `00-READ-FIRST`, and `docs/plans/execucao/` became `docs/plans/execution/`.
**A project scaffolded with the old spelling needs no action.** The old template name is still
accepted and resolves to the new one; and if the target already holds `docs/plans/execucao/` but not `docs/plans/execution/`,
the wizard keeps generating there instead of creating a second directory. Both cases print one
deprecation line on stderr and keep the same exit code; the fallback is guaranteed for one version.

## `templates/agents/AGENT.template.md` — the agent shape, with the prompt defense baseline

| File | Instantiated by the wizard? | Enforced by |
|---|---|---|
| `templates/agents/AGENT.template.md` | No — it is a reference, copied by hand when you add an agent | `tests/python/test_kits/test_prompt_defense_baseline.py` |

Copy it as the starting point of any agent you add, here or in your own project. It carries
the frontmatter shape (`name`, `description`, `tools` — always explicit, because an absent
`tools:` means *every* tool and reads as silence rather than as the widest permission there
is) and the **prompt defense baseline**: seven lines that say the agent does not switch role,
does not reveal secrets, emits no code or URL outside the request, treats unicode tricks and
claimed authority as attack signals, treats anything it reads as data rather than
instructions, refuses harm, and keeps to its granted scope — a read-only agent keeps Bash
read-only, a builder never widens its own reach. Every agent the product ships carries the block
in the wording its `tools:` earns, and the validator above fails an agent file that is missing any
clause or whose clause 7 disagrees with its tools (`scope-mismatch`) — a partial copy is not the
baseline. Adapted from ECC (MIT).

It deliberately lives in `templates/agents/` and not in `templates/`: the wizard's document
set is the non-recursive glob `templates/*.template.md`, so a file placed there would be
offered as a base document and written into `docs/plans/execution/` — right content, wrong
place.

## Undo

```
- Copy:    remove the agent-framework-wizard/ folder from the project
- Generated scaffold: remove operator-profile.yaml + docs/plans/execution/*.md by hand from
           the project where the wizard ran (there is no wiring/settings to undo)
```
