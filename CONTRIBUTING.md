# Contributing

Thank you. This repository is the **emitted product** — versioned modules, each sealed with
`CHECKSUMS.txt`. The module sources and the forge manifests live in the maintainers' private
tree and are **not** published here (`find . -name '*manifest*.y*ml'` returns nothing). That
shapes how a contribution works: you edit the emitted module in this tree and prove the change
with the tools that ship next to it; the maintainers fold the change into the source, re-emit
the module, and the checksums are regenerated on emission.

## Rules without exception

1. **No client name, personal e-mail, machine path, internal port or credential.**
   The `ip_pii_linter` runs before every emission and has no `--skip`. If it rejects, the problem
   is the content, not the linter.
2. **Every new `.py` in a module has a `--self-test`** that passes on Windows, macOS and Linux, and
   the self-test must not depend on a bare `python` (use `sys.executable`).
3. **Every `SKILL.md` passes `skill_lint`**: an I/O contract, at least 3 examples that were really
   executed (with the marker `<!-- executed: YYYY-MM-DD · exit=N -->`), a `## Proof` section, and
   paths anchored in `${CLAUDE_PLUGIN_ROOT}`.
4. **Hooks are WARN-only** unless an explicit decision, documented in the module's `hooks.json`,
   says otherwise.
5. **A bug fix ships with the test that failed before it.** A test written after the fix proves
   that today's code works; it does not prove that anything was fixed.
6. **A change to the harness, `hpp/<name>.py`, carries its tests under `tests/`** — in the file
   that already covers that module, or in a new `tests/test_<name>.py` (as `decision.py` and
   `policy.py` have) — and that file carries at least one test named `CONTROLE` that proves it can
   fail. A test file that cannot fail cannot be told apart from one that is absent.

## Flow

```bash
# 1. verify the module you are about to touch -- expect "status": "ok", exit 0
python installers/kit-forge-1.4.2/kit_doctor.py verify frameworks/operator-kit-1.7.0

# 2. edit the files INSIDE the emitted module (open an issue first if the change is large)

# 3. prove it with what ships in this tree
python installers/kit-forge-1.4.2/kit_doctor.py verify frameworks/operator-kit-1.7.0
python installers/kit-forge-1.4.2/tools/skill_lint.py --all frameworks/operator-kit-1.7.0/skills --run-proofs --json skill-lint.json
python -m hpp doctor
python -m hpp benchmark -k 3
python -m pytest tests -q

# 4. open the pull request against main. Do not touch CHECKSUMS.txt, the module .zip or the
#    module version -- all three are regenerated by the forge when the change is emitted.
```

Replace `frameworks/operator-kit-1.7.0` with the module you changed; the layout is
`<area>/<module>-<version>/`, and `marketplace.json` lists all of them.

What each command in step 3 tells you:

- **`kit_doctor.py verify`** compares every file against the module's `CHECKSUMS.txt`. After
  your edit it prints `"status": "corrupt"`, lists your files under `"mismatches"` (expected and
  actual sha256) and exits **2**. That is the expected result, not a failure to hide:
  `CHECKSUMS.txt` is written by the forge on emission, and the `mismatches` list must be exactly
  the files in your diff — a file you did not mean to change shows up there too. Do not regenerate
  the checksums by hand.
- **`skill_lint.py`** exits 0 (pass), 1 (warnings only) or 2 (at least one failure) over the lint
  findings. `--run-proofs` also executes the first command of each skill's `## Proof` block and
  records `proof.exit_code` in the `--json` report only — it does not change the exit code of the
  lint. Export `CLAUDE_PLUGIN_ROOT` to the module directory before running it, on a POSIX shell
  (on Windows the proofs run under `cmd.exe`, which does not expand `${CLAUDE_PLUGIN_ROOT}`). The
  JSON report is evidence for the pull request text; do not commit it.
- **`python -m hpp doctor`** must print `HPP doctor: ok`, and **`python -m hpp benchmark -k 3`**
  must end with `gate=PASS`. **`python -m pytest tests -q`** runs the harness suite (about a
  minute); all of it must pass.

## What the pull request carries

> Building a page, a report or a front end? Read
> [DESIGN.md](docs/DESIGN.md) first: it gives you the stylesheet as a file, the components that
> already exist, and the seven rules a reviewer will check. Reusing them is how a contribution
> looks like the project without anyone asking you to redo it.

- **The diff, confined to files inside one module** (plus the module's `README.md` /
  `README.pt-BR.md` pair when the behaviour you changed is documented there). Nothing under
  `CHECKSUMS.txt`, `*.zip`, `.claude-plugin/plugin.json` version fields or `marketplace.json`.
- **For a bug fix, the test that fails before and passes after**, in the module's own self-test
  or under `tests/`, together with a **control**: a case that passes on both sides, so the
  reviewer can see the test discriminates rather than fails for an unrelated reason.
- **The evidence, pasted as run:** the exit code and one line of output of every command in
  step 3 — including the `"status": "corrupt"` of `verify` with your files in `mismatches`.
  For a `SKILL.md` change, the `<!-- executed: YYYY-MM-DD · exit=N -->` markers refreshed with
  output you actually saw.
- **One entry under `## [Unreleased]` in `CHANGELOG.md` and in `CHANGELOG.pt-BR.md`**, with the
  same meaning in both.

What you cannot do from this tree, and do not need to: run
`kit_assembler.py --manifest ...` (the manifests are not published), regenerate `CHECKSUMS.txt`,
or bump a module version. Those are emission steps.

## What happens after merge

The maintainers fold your diff into the module source, bump the module version (semver — new
behaviour under the same number would break the `CHECKSUMS.txt` of whoever already has the
module), run the forge (`kit_assembler` with the `ip_pii_linter` gate), and re-emit the module:
new `CHECKSUMS.txt`, new `.zip`, `marketplace.json` and the catalogue regenerated. The
`CHANGELOG.md` entry you wrote travels with the release.

## Documentation in two languages

A document a **person** reads before deciding whether to use the project exists in both
languages, paired as `NAME.md` (English, the source of truth) and `NAME.pt-BR.md` (Brazilian
Portuguese). The first useful line of both is the language pair:

```
[English](NAME.md) · [Português](NAME.pt-BR.md)
```

A file an **agent** reads in order to execute — anything under `skills/`, `commands/`, `rules/`
or `agents/` — stays in English only. A translated copy there doubles the maintenance and
invites silent divergence between what the two copies instruct.

In practice, for a contributor:

- **Writing or changing a skill, command, rule or agent:** write it in English. Never add a
  `.pt-BR.md` next to it. Use the canonical section names that `skill_lint` checks — `## Contract`,
  `## Proof`, `## When NOT to Activate`, the `Priority:` header field, the `INPUT/OUTPUT/STATE IT
  TOUCHES` needles and the `<!-- executed: … -->` marker. The Portuguese forms (`## Contrato`,
  `## Prova`, `## Quando NÃO Ativar`, `Prioridade:`, `executado:`) are still accepted as legacy;
  new skills use the English ones (`SKILL-CONTRACT.md`, "Schema tokens").
- **Writing or changing a human document** (a `README.md`, anything under `docs/`, a root
  document): change both sides of the pair in the same pull request, keeping the same headings in
  the same order and byte-identical code blocks — a command is a command in any language. If you
  can write only one of the two languages, say so in the pull request and send that side
  complete; the maintainers write the other before emission. The English side is the one that
  binds.

A maintainer gate, run before every emission, rejects whoever breaks the
rule: a missing counterpart, a top link that does not point at the sibling, structural
divergence (the two sides carry the same headings, in the same order — translation changes
words, not structure), differing code blocks (a command is a command in any language), and any
`.pt-BR.md` inside the agent layer. `NOTICE`, `CITATION.cff` and `LICENSE` are legal and
citation instruments and stay in English only: a translation would create ambiguity about which
version binds.

## Commits and licence

- Conventional commits (`feat(kit):`, `fix(kit-forge):`, `docs:`).
- **By opening a pull request you agree that your contribution is licensed under this project's
  licence (MIT)** and you confirm you have the right to license it that way. No sign-off trailer
  or certificate is required — the pull request is the agreement.
- Do not send code you cannot license under MIT — including code generated from a repository
  without a licence.

## What is not welcome

- A new dependency where the stdlib solves it.
- An "improvement" on a neighbouring line that has nothing to do with the request (the diff has
  to trace back to the problem).
- An executed example that was not executed.
- A hand-edited `CHECKSUMS.txt`, `.zip` or module version — they move on emission, not in a
  pull request.
