01

O que é isto

Antes dos kits, uma pergunta mais simples: o que é um "kit" aqui, e por que ele precisa de uma forja em vez de só uma pasta zipada?

Um kit é um plugin de Claude Code auto-contido — skills, hooks, scripts e comandos que resolvem um problema específico (continuidade de sessão, coordenação entre sessões, health-check, RLS do Supabase...) e que cabem em qualquer projeto, não só neste repositório.

O problema que isso resolve: mecanismos que hoje só existem aqui — presos a caminhos, nomes de cliente e portas internas deste ecossistema — deveriam poder viajar. Mas "empacotar e copiar" sozinho cria dois riscos: (1) o pacote pode vazar dado que nunca deveria sair daqui, e (2) a documentação pode prometer um comportamento que o código não tem.

A regra de ouro do projeto Nenhum kit é aceito com base no que o texto diz que faz — só no que um comando real, rodado agora, prova que faz. Isso vale para cada skill, cada script, e para o próprio processo de montagem do kit.

É por isso que existe uma forja: um portão de qualidade e segurança pelo qual todo kit passa antes de ser considerado pronto para sair daqui.

02

A forja

kit-forge é o próprio primeiro kit do catálogo — a ferramenta que constrói e veta todos os outros. Nenhum kit sai sem passar por ela.

O caminho de um kit, do código-fonte ao pacote final, tem seis paradas. Nenhuma é opcional — e a terceira (o portão) não tem porta dos fundos: não existe flag --skip-lint.

1

manifest.yaml

Declara nome, versão, licença, de onde vêm os arquivos (source_root) e o que incluir/excluir do pacote final.

2

kit_assembler copia p/ staging

Resolve os globs de inclusão/exclusão e copia os arquivos reais para uma pasta temporária — o original nunca é tocado.

⛔

ip_pii_linter — o portão

Varre o staging por 7 categorias: segredo, cliente, infraestrutura interna, PII (CPF/CNPJ), identidade de marca, código de terceiro derivado, e higiene (.env, __pycache__...). Achado BLOCK = zero emissão. Ponto.

3

LICENSE + SANITIZACAO.md + CHECKSUMS.txt

Gerados automaticamente: a licença MIT, um relatório do que foi excluído/substituído, e o sha256 de cada arquivo do pacote.

4

troca atômica + zip determinístico

Só então o staging vira a pasta final (kit-1.0.0/). Rodar de novo sem mudar nada = no-op, não recria o zip.

5

kit_doctor confere o selo

Recalcula o sha256 de cada arquivo contra o CHECKSUMS.txt. Qualquer byte alterado depois da emissão = corrupt. (Prova disso no capítulo 05.)

O portão pegou um vazamento de verdade

Isto não é hipotético — aconteceu durante a montagem deste catálogo. Um exemplo "executado" de uma skill de auditoria usava, como dado de teste, o nome de um produto de um cliente real. O ip_pii_linter bloqueou a emissão apontando o arquivo e a linha exatos.

Incidente real · resolvido na fonte O nome do produto foi trocado por um genérico (billing_customers) e o exemplo foi re-executado de verdade — não editado por cima — para que a prova continuasse sendo uma prova. Duas outras categorias de vazamento apareceram do mesmo jeito: portas internas (:6001, :4002) em exemplos de código, e um arquivo de configuração pessoal que nunca deveria sair daqui. Os três casos foram corrigidos ou excluídos do pacote — nenhum foi só "ignorado".
Segundo incidente · o relatório de sanitização vazava o que escondia O SANITIZACAO.md que cada kit carrega listava, palavra por palavra, os padrões de exclude do manifesto — inclusive o nome de um arquivo interno excluído justamente por ser sensível. Um exclude existe para ocultar um nome; ecoar esse nome de volta no relatório público anulava a própria exclusão. Corrigido na fonte (kit_assembler.py): o relatório agora reporta só a contagem de exclusões aplicadas, nunca os padrões literais — vale para qualquer kit futuro, não só o de hoje.

O contrato que toda skill assina

Para uma skill entrar em qualquer kit, o SKILL-CONTRACT exige seis coisas — e um script (skill_lint.py) confere cada uma automaticamente:

04

O motor: /ralph-gate

O coração do operator-kit. Um loop autônomo que só para quando o trabalho está de verdade pronto — não quando alguém diz que está.

O plugin oficial ralph-loop da Anthropic já resolve bem a mecânica de loop: um hook de Stop que bloqueia até aparecer uma tag <promise>. O problema é que ele detecta texto — se o modelo escrever a tag, o loop acredita. O ralph_gate.py deste kit soma uma trava: a promessa só destrava a parada se um comando de verdade for re-executado dentro do processo do próprio hook, fora do alcance de quem está conversando.

Sem <promise> na fala → bloqueia

Se a última mensagem não contém a tag, o hook simplesmente devolve o mesmo mandato (charter) e conta mais uma iteração. Não pergunta "posso seguir?" — só continua.

Critério passa de verdade → libera

$ echo '{"...":"...", "stop_hook_active": false}' \
    | python hooks/ralph_gate.py
{}   ← libera a parada
ledger: gate-passed · estado removido

Texto forjado não engana — o exit-code é re-executado

Mesmo se o texto da mensagem fingir que um comando passou, o hook roda o comando de novo, no processo dele. Um arquivo-nonce confirma que a execução foi real, não copiada da conversa. Não dá para forjar o exit-code de um subprocess do harness.

Teto de iterações → parada legítima, não bloqueio eterno

ledger: paused-budget
"não terminei" ≠ "travado para sempre" — o loop libera sozinho
e registra que parou por orçamento, não por sucesso.

Os quatro cenários rodam três vezes seguidas, 12 checagens no total — a exigência para chamar algo de "confiável" não é passar uma vez, é passar sempre (pass^k = 1.00, k=3). Foi o resultado no card do operator-kit acima.

05

Prova ao vivo

Duas provas que você pode entender sem ler uma linha de código: o selo de integridade, e um ciclo real do /ralph-gate num repositório em branco.

O selo: 1 byte alterado quebra o hash

Cada kit emitido carrega um CHECKSUMS.txt — o sha256 de cada arquivo no momento da emissão. Clique para alterar um byte do README.md do operator-kit (exatamente o que foi testado de verdade) e veja o kit_doctor reagir.

operator-kit-1.3.0/README.md OK
esperado (CHECKSUMS.txt):
99c4640f204feda882ba3e2b5e7a5ae8787e0a67995f03d0d802a817201deab3
real (recalculado agora):
99c4640f204feda882ba3e2b5e7a5ae8787e0a67995f03d0d802a817201deab3
status: ok · mismatches: [] · kit_doctor exit 0

O dogfood: um ciclo real, num repositório em branco

Para provar que o operator-kit não depende deste ecossistema, ele foi copiado para um repositório git novo, vazio, fora deste projeto, e um ciclo completo de /ralph-gate foi rodado do zero — mandato real, falha real, correção real, aprovação real:

$ git init  &&  cp -r operator-kit-1.3.0/ ./operator-kit
$ cp operator-kit/profile.example.yaml operator-kit/operator-profile.yaml
$ python operator-kit/hooks/ralph_gate.py start \
    --charter "Crie build-ok.txt com o conteúdo 'ready'" \
    --criteria "python -c \"...sys.exit(0 if arquivo=='ready' else 1)\""
ralph-gate: armado (max_iterations=5, 1 critério)

$ <promise>TASK COMPLETE</promise>   (mas build-ok.txt ainda não existe)
{"decision": "block", "reason": "... FileNotFoundError ..."}

$ printf 'ready' > build-ok.txt
$ <promise>TASK COMPLETE</promise>   (agora existe, com o conteúdo certo)
{}   ← libera de verdade

$ cat .claude/handoff/HANDOFF-LEDGER.jsonl
{"event": "gate-failed", "failed_cmds": [...]}
{"event": "gate-passed"}

A primeira tentativa foi rejeitada porque o arquivo genuinamente não existia — não porque o kit "decidiu" desconfiar. A segunda passou porque o critério genuinamente passou. Nada disso foi simulado por fora: são comandos e códigos de saída reais, num repositório que nunca teve nenhum contato com este projeto.

06

Comece agora

O caminho de instalar o operator-kit num projeto novo em ~10 minutos — exatamente os passos usados no dogfood acima.

Copie a pasta do kit

Leve operator-kit/ (ou qualquer outro kit) para a raiz do projeto-alvo, ou para dentro de .claude/.

Crie o seu perfil

cp operator-kit/profile.example.yaml operator-kit/operator-profile.yaml — depois ajuste idioma, paths.*, autonomia.default, guardrails.protected_paths e os comandos reais de verificacao.done_criterios para o seu stack.

Rode os smoke tests

python operator-kit/_lib/profile_loader.py
python operator-kit/scripts/done_gate.py --self-test
python operator-kit/hooks/autoprompt_resume.py --print

Ligue os hooks (gate humano)

Editar settings.local.json é, por design, um passo manual — siga SETTINGS-WIRE.md e cole você mesmo. Ninguém deveria editar essa configuração automaticamente.

Arme o primeiro /ralph-gate

Com o hook ligado, use o comando de slash com um mandato e critérios reais do seu projeto. O loop só solta quando os critérios passarem de verdade — do jeito que você acabou de ver no capítulo 05.

07

Mini-curso

6 módulos, nesta ordem. Cada um fecha com um exercício real — sem simulação, sem "imagine que". Se você acabou de ler os capítulos 01-06, já fez metade do curso sem perceber.

O que é o House Party Protocol e por que existe

Objetivo: entender o problema que o marketplace resolve — kits soltos sem contrato de instalação nem prova de que funcionam fora da máquina do autor (capítulo 01).

Exercício: releia o callout "A regra de ouro do projeto" e explique, em 1 frase própria, por que "o texto diz" não basta.

O motor de instalação — os 6 estágios

Objetivo: rodar um plano de verdade, sem aplicar nada. detect → prereqs → profile → configure → wire-suggest → smoke, sempre nesta ordem, nunca bloqueando em input() de terminal — o "Confirm" é a dupla invocação plano→--apply.

$ python instaladores/kit-forge/kit_doctor.py install <algum-kit> --human
# leia a saída. Confirme: nada foi escrito (é o padrão).

Operator Kit — autonomia × intensidade

Objetivo: entender as 2 dimensões ortogonais do kit mais complexo. autonomy_level (0-5) decide QUEM aprova; intensidade (lite/full/ultra/off) decide QUANTO se verifica por ação. Um agente com autonomia alta e intensidade off é tratado como incidente, não como eficiência.

Exercício: abra rules/partial-autonomy-slider.md do operator-kit e ache a matriz de combinação das duas dimensões.

Continuidade + Lanes — por que a ordem de instalação importa

Objetivo: continuity-kit resolve "uma sessão não pode perder o próximo passo"; lane-kit resolve "N sessões não podem pisar uma na outra" — e usa o lane_id que o handoff do continuity-kit já grava. Instale continuity primeiro.

Exercício: no card do lane-kit (capítulo 03), ache a linha que declara essa dependência.

Os outros 5 kits — qual resolve qual problema

Objetivo: health-kit = saúde de serviço na statusline (+ dashboard Grafana/SigNoz desde v1.4.0). claude-dev-kit = construir suas próprias skills/hooks/plugins. supabase-pack = RLS + Edge Functions. agent-framework-wizard = scaffold de projeto novo sem travar em stdin. dev-squad-kit = squad de 12 papéis (PM/Architect/Dev/QA/DevOps/SM/PO/UX/ Data-Eng/Squad-Creator) quando o problema é "preciso de perspectivas diferentes", não código.

Exercício: para o seu próximo projeto, qual desses 5 (se algum) você instalaria primeiro? Escreva a razão em 1 frase.

Exercício final — instale 1 kit do zero

Objetivo: sair deste curso com um kit rodando de verdade, não só lido.

$ cp -r <kit>-<versao> seu-projeto/<kit>
$ cd seu-projeto
$ python <kit>/instaladores/kit-forge/kit_doctor.py install <kit> --target . --human
# leia o plano. Só se estiver de acordo:
$ python <kit>/instaladores/kit-forge/kit_doctor.py install <kit> --target . --apply
08

O que falta

Nenhum manual de verdade termina fingindo que está 100%. Três coisas ficaram de fora, e é melhor dizer do que esconder.

01

Dogfood no Mac M4

O ciclo real do capítulo 05 rodou em Windows. A perna de macOS não foi possível nesta sessão — não há acesso físico ou remoto à máquina a partir daqui.

02

Duas flags de linha de comando não existem como documentado

health_probe.py --profile example não é uma flag real — o jeito certo é a variável de ambiente OPERATOR_PROFILE=caminho.yaml (testado e funciona). E wire_settings.py exige --spec arquivo.yaml além de --target. Achados ao rodar de verdade, não escondidos atrás de "deveria funcionar".

03

5 kits sem README próprio — resolvido

Os 7 READMEs seguem hoje o mesmo molde de 9 seções (INSTALL-GUIDE-TEMPLATE.md): o que é, pré-requisitos, instalar via plugin/cópia, o que o instalador detecta, o que é seguro rodar de novo, wiring manual, prova real, desfazer. kit-forge também ganhou o README que faltava.

04

Zero instalação externa real ainda

Todo o dogfood até agora rodou em máquinas do próprio Max (Windows + o repositório em branco do capítulo 05). Nenhum terceiro instalou um kit deste marketplace num ambiente que o autor não controla — é o próximo teste que realmente prova portabilidade.
